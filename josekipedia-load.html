Load on Josekipedia

Background

Every position on this site comes from Josekipedia, a free joseki dictionary that its users write together. A site that makes practice problems automatically can send Josekipedia many more requests than someone browsing it by hand. To keep that load small, this site saves everything it gets and asks for as little as it can.

The Data

Josekipedia stores its joseki as a tree. Each point in the tree is a position, and its record lists the moves that can follow, how good each one is, and any comments and labels. This site asks for one of these records at a time, by its number, the same way Josekipedia's own pages do. A record is usually under a kilobyte.

Browsers don't let one website read another site's data unless that site allows it, and Josekipedia doesn't. So the site's requests go through a small proxy that runs on Cloudflare. The proxy also keeps a copy of everything it fetches, which is where most of the saving happens.

Caching

When the site needs a position, it checks the places below in order and stops at the first one that has it. Josekipedia is only asked when none of them do.

The first three are in your own browser:

  • Memory holds every position the page has used since you opened it.
  • Saved in your browser keeps every position you've used for a year, so when you come back the next day, positions you've already seen don't need any requests.
  • The browser cache is the browser's ordinary store for downloaded files. The proxy tells it to keep positions for 30 days.

The next two are on the proxy, so they're shared by everyone who uses the site:

  • Cloudflare's cache keeps positions for 30 days in each of the data centers Cloudflare runs. It's fast, but each data center has its own copy.
  • The shared database is a single store that every Cloudflare location reads from. It keeps each position for a year.

The empty board is a special case. Every game and every problem starts there, so its record (about 20 KB, with all the opening moves) is part of the site's own files. The site never asks the proxy or Josekipedia for it.

The Shared Database

When anyone's browser needs a position nobody has asked for yet, the proxy fetches it from Josekipedia and saves the answer. For the next year, everyone else who needs that position gets the saved copy.

This limits how much the site can ask for in total. Josekipedia's tree has about 220,000 positions. Even if visitors between them asked for every one, Josekipedia would see each request at most once a year, which is around 600 a day. The number is much lower in practice, because most practice happens in the same well-known joseki, and positions there get saved early and reused often.

The numbers so far match this. In its first day (14 to 15 October 2026), the shared database saved 1,101 positions, and the proxy sent 1,087 requests to Josekipedia: about one per position. As the database fills up, more and more requests are answered from it, and fewer go to Josekipedia.

Saved copies are refreshed after a year, in case Josekipedia's editors have changed something. A position is only fetched again when someone needs it, so old copies don't all expire and get refetched at once.

Simultaneous Requests

Two people can need the same new position at the same moment, for example if they're both working through the same joseki. If the second request arrives while the proxy is still waiting on Josekipedia for the first, it waits for that answer and uses it too. Cloudflare runs many copies of the proxy, and this works within each copy, which is where requests arriving together usually land.

Problem Searches

Problems are made by walking down Josekipedia's tree along a random joseki line, one move at a time, until the walk reaches a position that makes a good problem of the chosen type. Each step of the walk needs the next position's record.

A search can take several walks, since some walks end before reaching a usable position. With nothing saved yet, a search looks up about 70 positions on average. Once your browser has saved the common ones, most searches download only a few, and practicing with reviews downloads none. The site also limits what a search may ask for:

  • Download budget. A search stops starting new walks once it has downloaded 120 positions. This only affects unusual searches, like looking for a rare problem type from a starting point where it barely occurs.
  • The Next button. It's greyed out while a search runs, so impatient clicking can't start several searches at once.
  • Line length. Several problem types follow a joseki to its end. Each one stops at the longest line it can use, so it doesn't fetch positions it would throw away.
  • Add to Review. In Explore mode, it only checks the more expensive problem types when you pick one.
  • Ladders. For problems that depend on a ladder, the site may look ahead up to 25 positions to see where the ladder runs. It reads the joseki comments first, which often show the ladder already, and only looks ahead when they don't.

Prefetching and Crawling

  • The site doesn't fetch positions ahead of time. Downloading the positions around each step of a walk in advance would make the first searches faster, but it would also ask Josekipedia for many positions that never get used. So searches are slower at first, and speed up as the shared database fills.
  • It doesn't copy Josekipedia wholesale. Positions are only fetched when someone's practice needs them.
  • It only requests position records. It doesn't load Josekipedia's pages, images or search.

Development

Development creates load too, since testing means loading lots of problems. The local development server keeps every position it fetches in a folder on disk, so testing never asks Josekipedia for the same position twice, even across days. The automated tests don't contact Josekipedia at all. They run against small made-up trees.

Contact

If you run Josekipedia and want this site to change how it uses your data, please open an issue on GitHub or get in touch, and I'll change it. Thanks for making Josekipedia.
